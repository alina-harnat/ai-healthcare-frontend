## Coverage References

These references are derived from the inspected client implementation; they are not approved product acceptance criteria.

- **C-01:** Registration schema, default `User` role, Register mutation input, CurrentUser refetch, and navigation after successful registration. Sources: `modules/auth/schemas/register.ts`, `modules/auth/components/AuthForm/index.tsx`, `modules/auth/api/queries/index.ts`.
- **C-02:** The Supplier option maps to `Role.Admin`. Sources: `modules/auth/components/AuthForm/index.tsx`, `modules/common/enums/role.ts`, `modules/auth/locales/en.json`.
- **C-03–C-04:** Email validation via the registration schema and email input. Sources: `modules/auth/schemas/register.ts`, `modules/auth/components/AuthForm/index.tsx`.
- **C-05–C-08:** Password minimum length and lowercase, uppercase, and digit checks; the form currently uses the same translated validation text for these failures. Sources: `modules/auth/schemas/register.ts`, `modules/auth/components/AuthForm/index.tsx`, `modules/auth/locales/en.json`.
- **C-09:** Registration request failure is caught and surfaced in the form alert using the generic authentication fallback. Sources: `modules/auth/components/AuthForm/index.tsx`, `modules/auth/locales/en.json`.
- **C-10:** The submit button is disabled while registration is pending, and the submit handler guards against a second submission. Source: `modules/auth/components/AuthForm/index.tsx`.
- **C-11:** The registration form links to the sign-in route. Sources: `modules/auth/components/AuthForm/index.tsx`, `modules/auth/enums/auth-route.ts`.

## Unresolved Requirements and Coverage Limits

- No registration-specific acceptance criteria or manual testing checklist were found. The cases above cover observable behavior in the current client implementation and should be reconciled with product requirements when available.
- The registration API contract does not establish duplicate-email behavior, server-side role acceptance/authorization, email verification, or persistence/session expectations. TC-001 assumes configured successful Register and CurrentUser responses to exercise the client success path. TC-002 verifies only the outgoing role value and does not claim that the server accepts or persists it.
- No maximum password length, whitespace handling, or email normalization rule is documented; those behaviors are not asserted.
- The generic registration failure message currently says “We could not complete sign in.” Confirm the intended registration-specific error copy with product before treating that exact text as an acceptance criterion.
